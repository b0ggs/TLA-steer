# Repository instructions

This repository evaluates instruction files. It is not an instruction optimizer yet.

- `coder-outcome-evaluator-v2-implementation-plan.md` governs only its historical frozen feasibility-pilot evidence; `CODER_BENEFICIAL_SENSITIVITY_M2_IMPLEMENTATION_PLAN.md` is the sole active Milestone 2 authority, and no competing active plan may be created.
- Preserve raw run evidence.
- Never modify a target or candidate during a run.
- Never expose variant identity to the qualitative judge.
- Mechanical failures cannot be overridden by an LLM judge.
- Do not run live model calls in unit tests or CI.
- Use the Python standard library only unless the specification is explicitly amended.
- Run `python -m unittest discover -s tests -v` before handoff.

## Delegated-work orchestration controls

- These controls apply cumulatively whenever root delegates work, from the current user request through final handoff; splitting, restarting, or renaming work never resets them. If the user requests orchestration only, root makes no deliverable edits.
- Before the first delegated agent turn, root posts a concise brief that only restates or narrows existing authority: objective, named roles, writable paths or read-only status, forbidden actions, expected output, relevant validation, material milestones, and repair approach. Agent turns and tool/validation budgets are internal, task-proportionate controls: root may adjust them without user approval while the objective, authority, topology, writable paths, dependencies, live-call authority, destructive/integration authority, and edit caps stay unchanged, and discloses material adjustments in the next update. Unlisted roles and edit paths are forbidden. A brief may not create an earlier stop or reapproval gate unless required by the user or an applicable experimental no-retry rule.
- Before any task-related write or validation in a request that will use delegation, root records the Git dirty/untracked baseline. If delegation is proposed after either occurred without that baseline, root must reconstruct and verify the pre-task baseline or stop for user direction.
- An editing brief also sets two task-specific hard caps: number of changed/new deliverable paths and total textual churn (Git additions plus deletions, with untracked text counted as additions). Binary changes require an explicitly allowlisted path and are reported by status and byte change. Missing edit caps mean read-only.
- Prior user approval is required before expanding the objective or scope, writable paths, textual or binary churn caps, dependencies, features, destructive actions, live calls, agent topology, commits, pushes, or merges, or before weakening a user- or policy-imposed stop condition. It is not required for additional in-scope agent/tool/repair turns or necessary offline validation reruns within those boundaries.
- Root tracks agent invocations, validation attempts, and repair cycles as internal loop diagnostics; their counts never reset and do not themselves create user approval gates. A repair cycle starts with the first edit responding to a known failure and ends when validation or review resumes.
- Use one implementer at a time and at most one final read-only reviewer by default; audit and review loops are prohibited. Additional in-scope repair turns continue automatically. For an N-auditor-only request, those N one-turn read-only auditors replace the default roles and no final review is added.
- Subagents may not spawn other agents unless the user previously approved the named child roles. Root interrupts unauthorized delegation immediately. Only an implementer or repair role may edit allowlisted deliverables; root, auditors, reviewers, and test-only roles are read-only.
- Plans receive one consolidated revision and one final review unless the user explicitly authorizes additional rounds. Findings are blocking or optional; only in-scope blockers may enter repair, and optional work is deferred.
- After a repair edit, run one bounded focused validation covering the known failure and repository-enforced constraints directly bound to the edited paths before a full-suite validation. If it fails, do not run the full suite. Never rerun an unchanged validation against unchanged relevant inputs unless correcting a command-selection or infrastructure-invocation error; every repair must address a newly observed concrete failure, remain within the approved engineering boundaries, and preserve acceptance criteria.
- After every editable turn and validation, root checks the complete baseline-to-current status/diff, resolved paths, role/turn counts, and churn/path caps before any next action. Rename/copy collapsing is disabled. At handoff, report changed/new/deleted paths, additions and deletions separately, replacement-file final lines, binary changes, validations/results, deviations, and blockers.
- Root gives concise user updates at delegation start, material milestones, and handoff, including material adjustments to internal turn or validation budgets. Bookkeeping or reporting lapses are corrected and disclosed before the next stage; if the baseline or material facts cannot be verified, stop.
- Ordinary engineering uses the baseline, allowlist, diff, and offline validation. Strict containment, freezing, blinding, provenance records, and protocol no-retry rules apply only to experimental subjects, judges, hidden evidence, and live runs.
- Stop and interrupt agents if there is an unauthorized scope/path/action/topology change, edit-cap breach, prohibited information access, unverifiable baseline or material fact, no material diagnostic progress, the same root cause persists after two targeted corrections, a proposed correction crosses an actual authority boundary, or acceptance would be weakened. Experimental no-retry and stop rules always control live runs.
- This is a behavioral policy, not operating-system sandbox enforcement. Do not build enforcement infrastructure unless the user separately approves it.
