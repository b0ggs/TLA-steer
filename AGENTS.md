# Repository instructions

This repository evaluates instruction files. It is not an instruction optimizer yet.

- The sole active V2 program and CODER feasibility-pilot authority is `coder-outcome-evaluator-v2-implementation-plan.md`; do not create a competing active V2 plan.
- Preserve raw run evidence.
- Never modify a target or candidate during a run.
- Never expose variant identity to the qualitative judge.
- Mechanical failures cannot be overridden by an LLM judge.
- Do not run live model calls in unit tests or CI.
- Use the Python standard library only unless the specification is explicitly amended.
- Run `python -m unittest discover -s tests -v` before handoff.

## Delegated-work orchestration controls

- These controls apply cumulatively whenever root delegates work, from the current user request through final handoff; splitting, restarting, or renaming work never resets them. If the user requests orchestration only, root makes no deliverable edits.
- Before the first delegated agent turn, root posts a concise brief that only restates or narrows existing authority: objective, named roles and turn limits, writable paths or read-only status, forbidden actions, expected output, relevant validation, material milestones, and repair limit. The brief sets a finite, task-proportionate tool-call limit for each agent turn; increasing it requires prior user approval. Unlisted roles, turns, and edit paths are forbidden. A brief may not create an earlier stop or reapproval gate unless required by the user or an applicable experimental no-retry rule.
- Before any task-related write or validation in a request that will use delegation, root records the Git dirty/untracked baseline. If delegation is proposed after either occurred without that baseline, root must reconstruct and verify the pre-task baseline or stop for user direction.
- An editing brief also sets two task-specific hard caps: number of changed/new deliverable paths and total textual churn (Git additions plus deletions, with untracked text counted as additions). Binary changes require an explicitly allowlisted path and are reported by status and byte change. Missing edit caps mean read-only.
- Prior user approval is required before expanding scope, paths, dependencies, features, destructive actions, live calls, agent topology, caps, commits, pushes, or merges, or before weakening a user- or policy-imposed stop condition. Correcting a known failure requires no new approval while it remains within the existing authority and repair allowance. Root may adjust which task-proportionate, in-scope offline validations run within the brief's fixed validation-execution limit; increasing that limit requires prior user approval.
- Each spawn or resumed/follow-up agent invocation counts as one turn, including descendants. Each attempted execution of a test, lint, typecheck, build, smoke, render, or other validation counts separately even if it fails before collecting or executing tests, including repetitions inside wrappers or loops. A repair cycle starts with the first edit responding to a known failure and ends when validation or review resumes; a later repair edit starts another cycle. Limits never reset.
- Unless the user approves different limits, permit at most one implementer turn, at most one read-only reviewer turn, and at most two repair cycles; the brief sets a task-proportionate offline-validation limit and enough repair-role turns and focused validations to use its repair allowance. An in-scope failure continues automatically while allowance and all approved caps remain; it stops when the applicable limit is exhausted or correction would exceed existing authority. For an N-auditor-only request, those N one-turn read-only auditors replace the default agent allowances and no other agent turns are permitted without separate user approval; a final review counts within N.
- Subagents may not spawn other agents unless the user previously approved the named child roles. Root interrupts unauthorized delegation immediately. Only an implementer or repair role may edit allowlisted deliverables; root, auditors, reviewers, and test-only roles are read-only.
- Plans receive one consolidated revision and one final review unless the user explicitly authorizes additional rounds. Findings are blocking or optional; only in-scope blockers may enter repair, and optional work is deferred.
- After a repair edit, run one bounded focused validation covering the known failure and repository-enforced constraints directly bound to the edited paths before spending a full-suite validation. If it fails, do not run the full suite; automatically use the next available repair cycle only when the correction directly addresses the observed failure, does not weaken acceptance criteria, and remains within the approved objective, paths, dependencies, cumulative churn, agent turns, validation executions, and repair cycles. Calling work mechanical, trivial, or small grants no authority.
- After every editable turn and validation, root checks the complete baseline-to-current status/diff, resolved paths, role/turn counts, and churn/path caps before any next action. Rename/copy collapsing is disabled. At handoff, report changed/new/deleted paths, additions and deletions separately, replacement-file final lines, binary changes, validations/results, deviations, and blockers.
- Root gives a concise user update at delegation start, after each agent completes, after validation/review, and at handoff. Bookkeeping or reporting lapses are corrected and disclosed before the next stage; if the baseline or material facts cannot be verified, stop.
- Ordinary engineering uses the baseline, allowlist, diff, and offline validation. Strict containment, freezing, blinding, provenance records, and protocol no-retry rules apply only to experimental subjects, judges, hidden evidence, and live runs.
- An unauthorized scope/path/action/agent change, explicit cap/count breach, prohibited information access, unverifiable baseline or material fact, or unresolved failure after the repair limit is exhausted stops and interrupts agents and prohibits further writes, validations, review, and integration pending user direction.
- This is a behavioral policy, not operating-system sandbox enforcement. Do not build enforcement infrastructure unless the user separately approves it.
